# 架构与实现

```text
浏览器工作台
  ├─ POST /api/runs：创建任务或跟进修订
  ├─ GET /api/runs/:id/events：SSE 事件与断线续传
  └─ GET /api/runs/:id：恢复状态
           ↓
任务执行器 + 文件 checkpoint
           ↓
示例流程 / Chat Completions 工具循环
           ↓
统一工具入口 executeTool
  取数 → 可选修订 → 计算 → 校验 → 结构化报告
           ↓
报告预览 / Markdown / 打印 PDF
```

## Agent 与工作流

`runLive` 把用户目标和工具 schema 发送给兼容服务，将 `tool_calls` 交给统一工具执行器，回传工具结果，再由模型选择下一步。达到报告完成、等待补充、调用上限或异常时结束。示例模式 `runDemo` 使用固定流程，实际计算与状态变化仍由同一执行器完成，界面明确标注。

每次最多六轮模型请求、十二次工具调用。前端使用 SSE 接收执行事件，模型 HTTP 请求本身不是逐 token 流式。工具结果和模型 token usage 被记入任务事件，不存模型内部推理。

## 工具边界

| 工具 | 输入 | 前置条件与输出 |
|---|---|---|
| `get_meal_records` | 无 | 载入或复用合成记录 |
| `revise_rice_portion` | `grams` | 只能使用用户明确克数或当前份量的一半；使旧分析失效 |
| `calculate_nutrition` | 无 | 根据当前记录与每100g参考值计算并附证据 |
| `validate_report_data` | 无 | 明细与汇总、有效数值和来源检查 |
| `generate_report` | 无 | 必须已校验；不能接受模型传入营养数字 |
| `ask_user` | `question` | 持久化等待态并停止本轮 |

## 状态与恢复

任务状态为 `running / awaiting_input / completed / failed`。每个事件追加时，将完整任务写入同目录临时文件，再 rename 到 UUID 文件。SSE 支持事件序号和 Last-Event-ID，客户端按序号去重。

后续输入创建新的任务，复制前一任务的当前饮食记录，保留报告历史；修订生成新版本。失败重试保持版本，如果已有计算和校验则只重试生成报告。进程重启时把运行中的任务改为失败，说明原因并保留中间结果。

当前文件存储适合本机单进程。未来公开部署需要数据库事务或乐观锁、认证、幂等创建、队列和调用预算；不能直接多实例共享此目录。

## 数值与证据

计算从未四舍五入的原料贡献开始累加，再在展示层保留一位小数。校验允许逐行展示舍入带来的小误差，不把字段一致性当作营养准确率。

图表柱高是参考能量。营养色块按蛋白质/碳水/脂肪 4/4/9 能量比例归一化，仅作构成示意，图下明确说明两种口径。

## 本地访问

默认仅监听 `127.0.0.1`；限制 Host 和 Origin；模型密钥不会通过配置接口返回；静态文件有明确白名单，不能访问 `.env` 或 `.local`。模型错误只返回 HTTP 状态，不透传服务商响应体。真实模型依然只能接触此演示的合成记录。
